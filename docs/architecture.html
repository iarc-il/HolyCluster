HolyCluster — Architecture Guide

A maintainer-oriented explanation of how HolyCluster works, end to end. Markdown source: docs/ARCHITECTURE.md · Improvements: improvements.html

1 · What HolyCluster Is

HolyCluster (holycluster.iarc.org) is a real-time visualization of the amateur-radio DX cluster network. Ham operators worldwide report stations they hear ("spots": who heard whom, on what frequency, in what mode, when). HolyCluster aggregates spots from many sources, enriches them with geographic data, and draws them live on an interactive world map — and with the optional desktop CAT server, clicking a spot tunes the operator's physical radio.

DeliverableSourceWhat it is
Web applicationui/ + backend/React SPA served by FastAPI; live spots over WebSocket
Data platformbackend/Collectors ingesting telnet DX clusters + POTA/SOTA/WWFF into PostgreSQL/Valkey
Holy Cluster desktop appcatserver/Rust Windows app (MSI) bridging the web UI to the radio via OmniRig

4.2 The spot collection pipeline

flowchart LR
    subgraph SOURCES["Source tasks (asyncio)"]
        T1["Telnet clients<br/>one per cluster server"]

        S1["SOTA poller · 60s"]

    Q{{"asyncio.Queue<br/>maxsize 1000"}}
    subgraph CONSUMER["process_spots (single consumer)"]
        DEDUP["Dedup: Valkey SET NX<br/>key = time:dx:freq:spotter · TTL 60s"]
        ENRICH["enrich_spot<br/>band/mode + geo + dxpedition"]
        VALIDATE["validate<br/>callsign, band, locator"]
    end
    PG[("PostgreSQL<br/>holy_spots2")]
    STREAM[("Valkey stream-api<br/>maxlen 10000")]
    T1 --> Q
    P1 --> Q
    S1 --> Q
    W1 --> Q
    Q --> DEDUP --> ENRICH --> VALIDATE
    VALIDATE -->|"always"| PG
    VALIDATE -->|"if locator+band+mode present"| STREAM
    STREAM -->|"consumer group api-group"| APIB["api: spots_broadcast_task"]
    APIB -->|"WebSocket broadcast"| CLIENTS["All connected browsers"]
All sources feed one queue; one consumer enriches and persists. Sources also record arrivals to the stream-arrivals analytics stream.
  • Telnet clusters (collectors/telnet/): server list in telnet_servers.csv; one task per server, exponential reconnect backoff (60 s → 24 h), regex parsing, keepalive ping on 60 s silence. Spotters W3LPL and J9AQ are hardcoded-banned.
  • POTA/SOTA/WWFF: JSON pollers sharing run_json_spot_collector (dedup, arrival recording, error backoff ≤ 300 s).
  • There is no RBN or DXHeat collector — telnet clusters are the live feed.

4.3 Spot enrichment

sequenceDiagram
    participant C as process_spots
    participant BP as band_plans.json

    participant Q as QRZ.com XML API
    participant CTY as CTY file (in-process)

    C->>BP: band + mode from frequency (mode also from comment keywords)
    Note over C: missing band → spot dropped

        V-->>C: locator, lat/lon, dxcc, zones
    else cache miss

        Q-->>C: grid locator, state, zones
        C->>CTY: prefix → DXCC, continent (always — coords fallback if QRZ has no grid)

    end

    C->>PG: INSERT INTO holy_spots2
Both spotter and DX callsigns are geolocated — the map needs both arc endpoints.
The hardcoded override table for ~25 special callsigns lives in backend/shared/src/shared/geo.py:33-60 — this is where you add fixes per the fix_missing_spot.md runbook. The QRZ session key is refreshed hourly by the collector; the API's /locator returns 503 without it.

4.6 WebSocket protocol

One multiplexed socket, protocol version 1: every message is JSON with {"version": 1, "type": ...}.

sequenceDiagram
    participant B as Browser (useWs.jsx)
    participant A as api /ws
    participant S as Valkey stream-api
    B->>A: {version:1, type:"spots", action:"initial"}
    A-->>B: {type:"spots", spots:[...up to 500...]}
    loop live broadcast
        S->>A: XREADGROUP api-group
        A-->>B: {type:"spots", event:"update", spots:[...]}
    end
    Note over B,A: on reconnect → {action:"catch_up", last_time}
    B->>A: {version:1, type:"submit", spotter, dx, freq, comment}
    A-->>B: {type:"submit", status:"success"|"failure"}
    B->>A: {version:1, type:"missing", action:"start/add/finish", callsigns}
    A-->>B: batch callsign resolutions (4 workers × 50)
    B->>A: {version:1, type:"radio", ...}
    A-->>B: {type:"radio", status:"unavailable"}
    Note over B,A: radio messages only work when the socket passes through catserver
The radio type is a deliberate no-op on the backend — the catserver intercepts it locally when installed.

5 · The Frontend (ui/)

React 18 (JSX, no TypeScript) + Vite 6 + Tailwind. Formatter/linter: Biome. Tests: Vitest. The map is HTML5 Canvas + d3-geo (not Leaflet). In dev, Vite proxies all API/WS routes to holycluster-dev.iarc.org — npm run dev needs no local backend.

5.1 State management — the provider tree

All global state is React Context. ProfilesProvider is the backbone: nearly every persistent setting is a section of the "active profile" in localStorage.

5.4 Persistence

  • "profiles" (localStorage) — the entire multi-profile store; every write re-serializes and sanitizes it; legacy keys migrated on first load.
  • IndexedDB — history-spot interval cache with gap-fill and idle-time eviction every 3 h.
  • URL param — shareable filter links temporarily override profile filters.
  • No server-side accounts or sync — profiles export/import as JSON files in Settings.

6 · The CAT Server (catserver/)

A Rust desktop app (product name "Holy Cluster", HolyCluster.exe) bridging the remote web UI to the local radio.

6.1 The reverse-proxy trick

flowchart LR
    subgraph LOCAL["Operator's PC"]
        B["Browser at<br/>http://127.0.0.1:3000"]
        CS["catserver<br/>(axum server :3000)"]
        R["Radio<br/>OmniRig (COM) or rigctld :4532"]
        LOG["Logger (WSJT-X UDP)"]
    end
    REMOTE["holycluster.iarc.org<br/>(--dev-server → dev site)"]
    B -->|"all HTTP requests"| CS
    CS -->|"reverse-proxies pages, assets, API"| REMOTE
    B <-->|"/ws (one socket)"| CS
    CS <-->|"non-radio messages forwarded"| REMOTE
    CS <-->|"type: radio handled locally"| R
    CS -->|"HighlightSpot → UDP packet"| LOG
The same web UI gains radio control with no special "local mode": messages with version==1 && type=="radio" are handled locally; everything else is forwarded upstream.

A single-instance guard makes a second launch POST /open to the running instance. --local-ui serves a local ui/dist instead of proxying; --dummy uses a fake radio.

6.3 Radio control message flow

sequenceDiagram
    participant UI as Web UI (useRadio.jsx)
    participant CS as catserver /ws
    participant RIG as OmniRig / rigctld
    participant LOG as Logger (UDP)

7.2 Nginx routing and TLS

The authoritative config is backend/infra/nginx/nginx.conf.template, rendered at container start with envsubst '${DOMAIN}'. The committed nginx.conf next to it is a stale render — editing it does nothing. Blocks: :80 ACME + redirect · :443 proxy to api:8000 with WS upgrade · :9999 nginx-ui admin · :3000 passthrough to host Grafana.

sequenceDiagram
